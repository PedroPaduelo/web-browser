Riscos e Pontos Críticos

Identificação de riscos no sistema: limites de recursos, vazamentos de memória, condições de corrida e pontos de falha.

Limite de Displays

⚠️

Display Range :100-199

O sistema usa displays Xvfb de 100 a 199, limitando a 100 sessões simultâneas por instância. Se todas estiverem ocupadas, novas sessões falham.

// session-manager.js
const DISPLAY_MIN = 100;
const DISPLAY_MAX = 199;  // Máximo 100 sessões

function allocateDisplay() {
  for (let d = DISPLAY_MIN; d <= DISPLAY_MAX; d++) {
    if (!usedDisplays.has(d)) {
      usedDisplays.add(d);
      return d;
    }
  }
  return null; // Erro: No display available
}

Memory Leaks

🎯 ImageBitmap

No frontend, cada frame deve chamar bitmap.close() após usar. Caso contrário, memória GPU acumula.

ws.onmessage = (event) => {
  createImageBitmap(event.data).then((bitmap) => {
    ctx.drawImage(bitmap, 0, 0);
    bitmap.close(); // ⚠️ Obrigatório!
  });
};

🗑️ Cleanup de Sessões

Se o processo morrer abruptamente, Xvfb e Chrome podem ficar órfãos. O startup cleanup tenta resolver, mas não é garantido.

// index.js — limpeza na inicialização
execSync('pkill -f "Xvfb :[1-9][0-9][0-9]"');
for (let d = 100; d <= 199; d++) {
  unlinkSync(`/tmp/.X${d}-lock`);
  unlinkSync(`/tmp/.X11-unix/X${d}`);
}

Race Conditions

❌ Double-session-start

Usuário clica "Iniciar" duas vezes rápido. Pode criar duas sessões com mesmo tenant. Mitigação: disable button enquanto status === 'creating'.

⏱️ Timeout race

Se a sessão morrer minutos depois do timeout, o sessionDied callback pode disparar duas vezes. Atualmente o código ignora se sessão não existe mais.

🔄 CDP reconnect

Se o WebSocket do CDP cair, o CDPScreencast tenta reconectar até 5 vezes. Pode criar múltiplas conexões se não limpar timers corretamente.

Backpressure

O StreamManager verifica ws.bufferedAmount antes de enviar. Clientes muito lentos (mais de 4MB buffer) têm frames descartados.

// stream-manager.js
broadcastFrame(frame) {
  for (const ws of this.clients) {
    if (ws.bufferedAmount > 4 * 1024 * 1024) continue; // Skip
    ws.send(frame, { binary: true });
  }
}

⚠️ Isso causa perda de frames (video stutter), mas evita OOM no cliente.

Melhorias Recomendadas

🐛 Bugs

  • Lock files nem sempre são limpas após crash
  • Timeout warning não está implementado no frontend
  • Profile merge pode sobrescrever mudanças

🚀 Performance

  • Considerar usar WebRTC para reduzir latência
  • Implementar selective streaming (somente área dirty)
  • Compressão adicional (WebP se disponível)

🔒 Segurança

  • Rate limit por tenant (não só por IP)
  • Audit log de todas as ações
  • TLS obrigatório para WSS
  • Sandbox mais restritiva no Chrome

📈 Escala

  • HPA/K8s para múltiplas instâncias
  • Shared nothing entre instâncias
  • Redis pub/sub para multi-instância stream
