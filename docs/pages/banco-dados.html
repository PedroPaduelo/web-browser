💾 Banco de Dados

Visao Geral

O Serende utiliza SQLite via better-sqlite3 como banco de dados embarcado. Configurado em modo WAL (Write-Ahead Logging) para melhor performance de leitura concorrente. Foreign keys estao habilitadas. O arquivo do banco fica em /data/serende.db.

Schema

O banco possui uma unica tabela, api_keys, que armazena credenciais e configuracoes por tenant:

CREATE TABLE api_keys (
  id TEXT PRIMARY KEY,            -- SHA256(apiKey).slice(0,16) = tenantId
  key_hash TEXT NOT NULL UNIQUE,  -- SHA256 completo da API key
  key_prefix TEXT NOT NULL,       -- Primeiros 10 chars (ex: "sk_a1b2c3...")
  name TEXT NOT NULL,             -- Nome descritivo
  enabled INTEGER DEFAULT 1,     -- 0=revogado, 1=ativo
  max_sessions INTEGER DEFAULT 100,
  max_session_duration INTEGER DEFAULT 3600,
  max_idle_timeout INTEGER DEFAULT 300,
  features TEXT DEFAULT '{}',     -- JSON de feature flags
  created_at TEXT DEFAULT (datetime('now')),
  last_used_at TEXT               -- Atualizado no login
);

O id e derivado do hash da API key (primeiros 16 chars do SHA256), servindo simultaneamente como identificador do tenant em todo o sistema.

Modulos

db.js

Modulo de conexao SQLite. Configura o path /data/serende.db, ativa WAL mode via PRAGMA journal_mode=WAL, habilita foreign keys com PRAGMA foreign_keys=ON. Executa CREATE TABLE IF NOT EXISTS api_keys no init para garantir que o schema existe.

key-store.js

CRUD completo de API keys. Funcoes: createKey(), listKeys(), validateKey(), updateKey(), revokeKey(), regenerateKey(), migrateFromEnv(). Todas as operacoes usam prepared statements para seguranca e performance.

Operacoes

Operacao Metodo Descricao
Criar key createKey(name, opts) Gera sk_ + 32 hex chars, salva SHA256 hash no DB
Validar validateKey(apiKey) Calcula SHA256 do input e busca o hash no banco
Listar listKeys() Retorna todas as keys sem hash/secret (so prefix e metadata)
Revogar revokeKey(id) Seta enabled = 0, key para de funcionar imediatamente
Regenerar regenerateKey(id) Gera nova raw key mantendo o mesmo id/tenant
Migrar migrateFromEnv(apiKey) Importa AUTH_API_KEY legacy do .env para o SQLite

Dados em Memoria

Alem do SQLite, diversos dados criticos vivem exclusivamente em memoria (perdidos ao reiniciar o processo):

  • sessionResources (Map): StreamManager + InputHandler por sessao. Contem referencias aos processos Xvfb, Chrome e FFmpeg.
  • cdpPools (Map): Conexoes CDP (Chrome DevTools Protocol) reutilizaveis por sessao, com timeout de 30 segundos para reciclagem.
  • loginAttempts (Map): Contagem de tentativas de login por IP para rate limiting. Limpa automaticamente apos janela de 1 minuto.
  • activeWsConnections (Map): WebSocket connections ativas indexadas por token, usadas pelo checker periodico de expiracao.

Backup

Procedimento de Backup

  • Arquivo principal: /data/serende.db
  • WAL mode gera arquivos auxiliares: -wal e -shm junto ao DB
  • Para backup seguro (consistente): sqlite3 /data/serende.db ".backup /tmp/backup.db"
  • Nunca copiar o .db diretamente enquanto o servidor estiver rodando (pode corromper)
  • Profiles de navegacao ficam em /data/tenants/ (filesystem, nao no DB) e devem ser incluidos no backup
