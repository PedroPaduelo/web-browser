💾 Banco de Dados

SQLite

O Serende utiliza SQLite como banco de dados primário para armazenamento de metadados.

  • Local: ./data/serende.db
  • Tipo: Embedded (sem servidor separado)
  • ACID: Suporte completo a transações
  • 🔄 Fluxo Completo

Schema

-- Tenants
CREATE TABLE tenants (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  expires_at DATETIME,
  active INTEGER DEFAULT 1,
  metadata TEXT
);

-- API Keys
CREATE TABLE api_keys (
  id TEXT PRIMARY KEY,
  tenant_id TEXT NOT NULL REFERENCES tenants(id),
  key_hash TEXT NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  expires_at DATETIME,
  active INTEGER DEFAULT 1
);

-- Sessions (opcional - pode ser em memória)
CREATE TABLE sessions (
  id TEXT PRIMARY KEY,
  tenant_id TEXT NOT NULL REFERENCES tenants(id),
  status TEXT DEFAULT 'creating',
  resolution TEXT,
  start_url TEXT,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  expires_at DATETIME
);

-- Indexes
CREATE INDEX idx_api_keys_tenant ON api_keys(tenant_id);
CREATE INDEX idx_sessions_tenant ON sessions(tenant_id);
CREATE INDEX idx_sessions_status ON sessions(status);

Tabelas

Tabela Descrição Tamanho típico
tenants Organizações/contas ~1 KB (poucos registros)
api_keys Chaves de acesso ~1 KB
sessions Histórico de sessões ~10 KB (por 1000 sessões)

Módulos de Acesso

  • key-store.js: CRUD de API Keys
  • tenant-manager.js: CRUD de Tenants
  • session-manager.js: Gerenciamento de sessões (em memória)
  • 🔄 Fluxo Completo

Backup

# Backup manual
cp data/serende.db data/serende.db.backup

# Backup automático (cron)
0 2 * * * cp /path/to/data/serende.db /backup/serende-$(date +\%Y\%m\%d).db

Manutenção

  • VACUUM: Reorganiza o banco periodicamente
  • ANALYZE: Atualiza estatísticas para queries
  • Cleanup: Remover sessões expiradas
  • 🔄 Fluxo Completo
-- Limpar sessões antigas (> 30 dias)
DELETE FROM sessions WHERE created_at < datetime('now', '-30 days');

-- VACUUM para recuperar espaço
VACUUM;

-- Verificar integridade
PRAGMA integrity_check;

Dados em Memória

Alguns dados são mantidos em memória para performance:

  • Sessões ativas: Map em memória (session-manager)
  • Streams ativas: Referências a processos
  • WebSocket clients: Lista de clientes conectados
  • 🔄 Fluxo Completo

Esses dados são não-persistentes — reiniciando o servidor, todas as sessões ativas são perdidas.

Perfil (Profile Data)

Dados de perfil (cookies, cache, etc) são armazenados no filesystem, não no SQLite:

/data/profiles/
└── {tenant-id}/
    └── master/
        ├── .config/google-chrome/
        │   └── Default/
        │       ├── Cookies
        │       ├── Local Storage/
        │       └── History
        └── .cache/
            └── google-chrome/
                └── Default/
                    └── Cache/
