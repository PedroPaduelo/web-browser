Key Store Agent

Gerenciamento seguro de API Keys com isolamento multi-tenant

Ativo key-store.js

Visão Geral

O Key Store Agent é responsável pelo ciclo de vida completo das API keys no sistema Serende. Ele gerencia a criação, validação, revogação e rotação de chaves, armazenando-as de forma segura em SQLite com hashing SHA256. O agente garante isolamento completo entre tenants através do derivation da tenant ID a partir da própria chave.

Schema do Banco de Dados

Tabela api_keys
Coluna Tipo Descrição
id UUID PRIMARY KEY Identificador único da chave
key_hash TEXT NOT NULL Hash SHA256 da chave completa (não reversível)
key_prefix TEXT NOT NULL Primeiros 8 caracteres da chave para identificação visual (ex: sk_prod_)
name TEXT NOT NULL Nome descritivo da chave (ex: "Integração CRM", "App Mobile")
enabled INTEGER DEFAULT 1 Flag de status (1 = ativa, 0 = revogada)
max_sessions INTEGER DEFAULT 10 Número máximo de sessões simultâneas permitidas
max_session_duration INTEGER DEFAULT 3600 Duração máxima da sessão em segundos (padrão: 1 hora)
max_idle_timeout INTEGER DEFAULT 900 Timeout de inatividade em segundos (padrão: 15 min)
features TEXT (JSON) Configuração de features como JSON (ex: {"webScraping":true, "screenshot":true})
created_at TIMESTAMP DEFAULT NOW() Data de criação da chave
last_used_at TIMESTAMP NULL Timestamp da última validação bem-sucedida

Funções

API do agente
Função Retorno Descrição
hashKey(apiKey) Promise<string> Calcula hash SHA256 da API key para armazenamento seguro. A chave original nunca é persistida.
deriveTenantId(apiKey) string Extrai tenant ID dos primeiros 16 caracteres do hash. Permite isolamento automático sem tabela de mapeamento.
generateRawKey() string Gera nova chave no formato sk_ + 32 caracteres hexadecimais aleatórios (128 bits de entropia).
createKey(name, options) Promise<object> Cria nova chave com configurações personalizadas. options inclui: maxSessions, maxSessionDuration, maxIdleTimeout, features. Retorna objeto com id e apiKey ( valor em claro exibido apenas uma vez).
listKeys(filters?) Promise<array> Lista todas as chaves com metadados (sem valores.hash). Suporta filtros opcionais por enabled, tenantId.
getKeyById(id) Promise<object> Busca chave por UUID. Retorna dados exceto key_hash.
updateKey(id, fields) Promise<void> Atualiza campos da chave. Permite modificar name, enabled, limites de sessão e features.
revokeKey(id) Promise<void> Desabilita chave definindo enabled = 0. Chaves revogadas são mantidas para histórico e auditoria.
validateKey(apiKey) Promise<object|null> Valida chave recebida: calcula hash, busca no banco, verifica enabled. Se válida, retorna configuração e atualiza last_used_at. Retorna null se inválida.
getStats() Promise<object> Retorna estatísticas: totalKeys, activeKeys, revokedKeys.
regenerateKey(id) Promise<string> Gera novo valor para chave existente mantendo o mesmo ID e configurações. Retorna o novo valor em claro (exibido apenas uma vez).
migrateFromEnv(apiKey, meta) Promise<object> Migra chave legada do .env para o banco SQLite. Usado durante onboarding inicial. meta inclui name e opções.

Segurança

Proteções e garantias

Camadas de Segurança

Hash SHA256

A chave em texto claro é imediatamente hasheada com SHA256 e o hash é persistido. O valor original nunca é armazenado, garantindo que mesmo em caso de vazamento do banco de dados as chaves não possam ser recuperadas.

Derivação de Tenant

O tenant ID é derivado dos primeiros 16 caracteres do hash SHA256. Isso cria isolamento natural no próprio dado da chave — diferentes tenants não podem acessar chaves umas das outras sem tabela de mapeamento.

Key Prefix

Armazenamos os primeiros 8 caracteres (key_prefix) para identificação visual e debugging. Isso permite operações como listar "tokens que começam com sk_prod_" sem comprometer a segurança da chave completa.

Revogação Suave

Chaves revogadas mantêm-se no banco para fins de auditoria. A flag enabled = 0 causa rejeição imediata na validação, mas o histórico e configurações são preservados.

Estrutura da Chave

sk_[prefix]_[random-hex] Exemplos: sk_prod_8f3a1b2c4d5e6f7a8b9c0d1e2f3a4b5c sk_test_a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6 sk_dev_11223344556677889900aabbccddeeff

Boa Práticas

  • Rotacione chaves regularmente usando regenerateKey()
  • Revogue imediatamente chaves comprometidas ou de funcionários que deixaram a organização
  • Configure limites apropriados de sessão para cada tipo de uso
  • Use features para principle of least privilege por chave
  • Nunca exponha chaves em logs ou URLs — sempre use headers Authorization
  • Adote diferentes chaves por ambiente (dev/staging/prod)

Migração de Legacy

Compatibilidade com configuração .env

Durante a transição de chaves armazenadas em variáveis de ambiente para o banco SQLite, o método migrateFromEnv() permite importar uma chave legada mantendo seu valor e adicionando metadados como nome e configurações.

// Exemplo de migração const result = await keyStore.migrateFromEnv(process.env.API_KEY_LEGACY, { name: 'Legacy Production Key', maxSessions: 20, maxSessionDuration: 7200, features: { webScraping: true, screenshot: true } }); console.log(`Chave migrada com ID: ${result.id}`);

Após a migração, a chave legada continua funcional mas agora está registrada no banco com todas as funcionalidades de gestão disponíveis.
