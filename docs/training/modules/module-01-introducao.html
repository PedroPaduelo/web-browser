Módulo 1: Introdução ao Serende

Entenda a arquitetura, componentes e casos de uso do sistema de browser remoto com streaming em tempo real.

Duração estimada 30 minutos
Público-alvo Administradores e usuários avançados
Pré-requisitos Nenhum (recomendado: conhecimentos básicos de browser)

🎯 Objetivos deste módulo

  • Compreender o que é o Serende

    Entenda o propósito do sistema: acesso remoto a browsers via streaming, com controle total de input e isolamento por tenant.

  • Conhecer a arquitetura de agentes

    Identifique os 15 agentes lógicos que compõem o sistema e suas responsabilidades.

  • Visualizar o fluxo de dados

    Entenda como as requisições fluem desde o frontend até o Chrome e retornam via streaming.

  • Identificar casos de uso

    Saiba quando utilizar o Serende vs soluções alternativas.

📋 O que é o Serende?

Definição rápida: Serende é um sistema de browser remoto com streaming em tempo real que permite controlar instâncias headless do Chrome via WebSockets e HTTP, com isolamento completo entre tenants (clientes).

Características principais

  • Streaming MJPEG via FFmpeg — captura da tela do Xvfb e codificação em tempo real
  • Controle completo de input — mouse, teclado e scroll via protocolo CDP (Chrome DevTools Protocol)
  • Isolamento por tenant — cada cliente tem sua própria chave API e espaço de arquivos isolado
  • Autenticação JWT — tokens assinados com HS256, validados em cada requisição
  • Escalabilidade horizontal — múltiplas sessões paralelas, pool de displays Xvfb
  • Admin panel — painel para monitoramento de sessões e gestão de chaves
  • SSE opcional — eventos de atividade e métricas via Server-Sent Events
  • Gravação de sessões — opcional via perfil (profile) do usuário
⚠️ Uso planejado: Este sistema foi desenvolvido para ambientes controlados e autorizados. Não use para acesso não-autorizado a sistemas alheios.

🔄 Fluxo de dados completo

Cada sessão de browser segue este fluxo end-to-end:

1. AUTH Frontend → POST /api/auth/login ↓ validateKey(key-store) + generateToken(JWT) ↓ returns: { token, tenantId } 2. SESSION START Frontend → POST /api/sessions (Authorization: Bearer) ↓ tenantManager.getOrCreate(tenantId) ↓ sessionManager.createSession() ├─ Xvfb :99+N ├─ Chrome --remote-debugging-port=9222 └─ FFmpeg -f x11grab → MJPEG stream 3. STREAMING GET /api/sessions/:id/stream?token=… ↓ streamManager.getMJPEG(sessionId) ├─ FFmpeg stdout pipe (boundary--) └─ streaming response (multipart/x-mixed) 4. VIEWER (Frontend) <img src="/api/sessions/…/stream"> OR WebSocket /ws/stream → recebe MJPEG chunks ↓ render em <canvas> ou <img> 5. INPUT POST /api/sessions/:id/input ↓ inputHandler.sendInput({type, x, y, key}) ├─ Node → Python stdin pipe └─ python-xlib (XTest) → Xvfb display Alternativa: WebSocket /ws/input 6. CDP COMMANDS POST /api/cdp/:port/:method ↓ cdpProxy.cdpRequest(port, method, params) ├─ WS ws://localhost:cdpPort/json └─ envia JSON-RPC, recebe resposta 7. SESSION END DELETE /api/sessions/:id ↓ sessionManager.destroySession(sessionId) ├─ kill Chrome, FFmpeg, Xvfb └─ limpar arquivos + timeout cleanup

⚡ Latência típica: 80–150ms round-trip (captura + rede + render).

🎯 Casos de uso recomendados

✅ Use o Serende para:

  • Automação de testes UI — RPA, testes E2E, validação de fluxos de navegação.
  • Monitoramento de sites — Captura de screenshots, verificação de disponibilidade e conteúdo.
  • Demonstrações remotas — Compartilhar uma sessão de navegação com clientes.
  • Extração de dados Headless — Navegação automatizada com input controlado (cliques, scroll, form submit).
  • Sessões de debugging — Revirar problemas de front-end em páginas específicas.
  • Automação de workflows — Preencher formulários automatizados com validação visual.

❌ NÃO use o Serende para:

  • Visualização multimídia pesada — Streaming de vídeos YouTube/Netflix terá baixa qualidade pois é MJPEG, não H.264.
  • Jogos ou-animacoes intensivas — Latência e frame rate limitados (~10–15 FPS).
  • Alto volume paralelo — Cada sessão consome Xvfb + Chrome + FFmpeg (~200–400 MB RAM). Escalabilidade requer orquestração externa.
  • Persistência de dados entre sessões — Sessions são efêmeras; use Download se precisar de arquivos.
  • Cargas de trabalho GPU — Chrome roda sem GPU com --disable-gpu.
