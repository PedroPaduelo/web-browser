🏗️ Arquitetura do Sistema Visão Geral

Visão Geral

O Serende é um sistema de browser remoto via streaming que permite controle de instâncias Chrome headless através de uma interface web.

4201
Porta do Servidor
30
FPS de Streaming
10
Sessões Simultâneas
30min
Timeout de Inatividade

Camadas da Arquitetura

Camada Responsabilidade Tecnologias
Frontend Interface React com visualização do browser remoto React 18, Vite 6, WebSocket
API Gateway REST API + WebSocket com autenticação JWT Express, ws, CORS, Helmet
Session Manager Orquestração de sessões Chrome Xvfb, Chrome CDP
Stream Manager Codificação e broadcasting de vídeo FFmpeg, MJPEG streaming
Input Handler Simulação de inputs (mouse/teclado) X11 Python, python-xlib
Data Layer Armazenamento de chaves e perfis SQLite, File System

⚠️ Análise de Riscos Vulnerabilidades & Mitigações

Matriz de Riscos de Segurança

Risco Severidade Mitigação Implementada Status
Accesso não autorizado a sessões Alta • JWT com expiry (24h padrão)
• Verificação por tenantId em todas as rotas
• WS valida token e sessão no upgrade 		Mitigado
Exfiltração de dados entre tenants Alta • Isolamento físico de diretórios (data/tenants/<id>)
• Session Manager valida tenantId antes de operations
• file system permissions 		Mitigado
DoS via session creation Média • Rate limit global em /api/ (100 req/min)
• Limite por tenant (maxSessions)
• Limite global (MAX_SESSIONS) 		Mitigado
Brute force em API keys Média • Rate limit específico em /api/auth/login (5 attempts/60s por IP)
• Key hash storage (não armazena key plain) 		Mitigado
leakage de console logs Média • Struct logging + requestId
• Production: oculta stack traces (erro 500 genérico)
• Helmet security headers 		Mitigado
CORS misconfiguration Média • CORS_ORIGIN configurável por env
• Default: permissivo para compatibilidade local
• Credentials habilitado 		Parcial
Session fixation / hijacking Média • JWT signed com segredo forte
• Token associado à sessão
• WS verifica token em intervalos (60s checker) 		Mitigado
Injection via CDP commands Alta • Somente endpoints autenticados
• CDP requests validated por sessionId
• Não há eval direto de user input (a não ser explicitamente /api/evaluate) 		Parcial
Resource exhaustion (display pool) Média • Display pool limitado (100-199 = 100 displays)
• Auto-cleanup de displays em 2s
• Session timeout com merge profile 		Mitigado
Persistence de malware nos profiles Alta • Profiles são por-tenant (tenant isolation)
• Sem download auto-execution
• Chrome com flags de segurança (--no-sandbox, --disable-gpu) 		Parcial

Gaps de Segurança Identificados

  • CORS default permissivo — Produção deve definir CORS_ORIGIN específico
  • --no-sandbox no Chrome — Necessário em container mas mitiga isolamento
  • Sem rate limit por tenant individual — Apenas global + maxSessions
  • SQLite sem criptografia — Dados em disco não criptografados
  • Logs sensíveis no console — requestId, tenantId aparecem em logs
  • Sem pii encryption — Cookies e dados de login armazenados plain
  • WebSocket sem subprotocol security — Apenas token query param
  • /api/evaluate permite código arbitrário — Endpoint perigoso exposto (deveria ser admin-only)

📖 Guia de Uso Como Usar o Sistema

1. Autenticação

Acesso via API Key. Cada tenant recebe uma chave no formato sk_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx.

POST /api/auth/login
Content-Type: application/json

{
"apiKey": "sk_0123456789abcdef..."
}

Resposta: { "token": "eyJhbG...", "tenantId": "abc123...", "userId": "abc123..." }

Armazene o token no localStorage ou sessionStorage. Ele será usado em todas as requisições via header Authorization: Bearer <token>.

2. Criar uma Sessão

POST /api/session
Authorization: Bearer <token>
Content-Type: application/json

{
"resolution": "1280x720",
"startUrl": "https://www.google.com"
}

Resposta: { "sessionId": "uuid", "status": "running", "resolution": { "width": 1280, "height": 720 } }

3. Conectar ao Stream

Após criar a sessão, conecte via WebSocket para receber os frames MJPEG:

ws://dominio:4201/ws/stream?token=<JWT>&sessionId=<sessionId>

O servidor enviará frames binários MJPEG continuamente. Renderize em um <canvas> com ctx.drawImage(video, 0, 0) ou use Blob URL.

4. Enviar Input (Mouse/Teclado)

POST /api/input
Authorization: Bearer <token>
Content-Type: application/json

{
"sessionId": "uuid",
"type": "mousemove",
"x": 512,
"y": 384,
"button": 0
}

Tipos: mousedown, mouseup, mousemove, keydown, keyup, wheel, scroll.

5. Navegação e Controle

POST /api/navigate/:sessionId
{ "url": "https://exemplo.com" }
POST /api/evaluate/:sessionId
{ "script": "document.title" }
GET /api/screenshot/:sessionId
← Retorna image/jpeg

6. Timeout e Cleanup

Sessões possuem timeout de inatividade padrão de 30 minutos. O sistema envia warning aos 28 minutos e finaliza automaticamente. Ao finalizar, o perfil do tenant é mergeado de volta para o profile-master, mantendo cookies, histórico e configurações.

⚙️ Painel Administrativo Gestão Completa

Acesso ao Admin

O painel administrativo está em /admin e requer a variável ADMIN_SECRET configurada no .env.

ADMIN_SECRET=seu-segredo-super-forte-aqui
Acesso: https://dominio/admin

A senha deve ser enviada no header X-Admin-Secret em todas as requisições administrativas.

Funcionalidades do Admin

  • Gestão de API Keys: Criar, listar, atualizar, regenerar e revogar chaves de acesso de tenants
  • Controle de Sessões: Visualizar todas as sessões ativas em todos os tenants, com tenantName, timeout info
  • Estatísticas: Total de keys ativas, sessões ativas, uptime do servidor, uso de memória
  • Configuração: Cada key pode ter limits customizados (maxSessions, maxSessionDuration, maxIdleTimeout, features JSON)
